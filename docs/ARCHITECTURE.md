# Tracraft Dash Round — архитектура

Версия документа: 0.1 (черновик, правится по ходу проектирования)

## Главный принцип

**Один JSON-контракт, два рендерера.** Схема лейаута описывает экраны, виджеты, их
геометрию и привязки к сигналам. Её умеет рисовать и прошивка (C++), и веб-редактор
(TypeScript). Редактор не генерирует код — он выдаёт файл, который прошивка исполняет
в рантайме. Поэтому набор виджетов держим маленьким, а правила геометрии — жёсткими:
любое расхождение между браузером и устройством убивает доверие к редактору.

## Железо

| Узел | Решение | Примечание |
|---|---|---|
| MCU | ESP32-S3R8, 2×LX7 @240 МГц | 16 МБ flash QIO, 8 МБ PSRAM OPI |
| Дисплей | AMOLED 1.75", 466×466, QSPI, **CO5300** | 434 КБ на кадр в RGB565; фреймбуфер целиком лежит в PSRAM |
| Тач | **CST9217** по I2C | свайпы между экранами; пока не задействован |
| CAN | встроенный TWAI + трансивер SN65HVD230 или TJA1051T/3 | CAN 2.0B, 500 кбит/с |
| Давление/NTC | ADS1115 по I2C, питание 5 В, gain 2/3 | Bosch PST-F: 0.5…4.5 В + встроенный NTC |
| EGT | MCP9600 по I2C | выбран вместо MAX31855 (SPI) ради экономии пинов |
| IMU | I2C | возможно уже стоит на плате |
| Частотные входы | PCNT периферия ESP32 | обороты/скорость/расход, нужна развязка входа |
| Питание | 12 В → защита → 5 В → плата | плюс вход «зажигание» на GPIO через делитель |

**Бюджет пинов — главное ограничение.** QSPI-дисплей забирает ~7 GPIO, поэтому всё
внешнее вешаем на одну шину I2C (ADC, термопара, IMU, тач) и оставляем 2 пина под CAN,
1–2 под частотные входы и 1 под сигнал зажигания. Никакого внешнего SPI, если можно
обойтись I2C.

## Слои

### 1. Драйверы и HAL
Инициализация QSPI-дисплея, тача, TWAI, I2C-шины, PCNT. Пины собраны в один
`include/board_pins.h`, чтобы смена платы не расползалась по коду.

### 2. Шина сигналов — ядро системы
Единая таблица слотов (~256), каждый слот: значение `float`, метка времени, флаг
валидности, источник, единица измерения, диапазон, счётчики min/max. Публикуют
CAN-декодер, опрос датчиков и вычисляемые каналы; подписываются виджеты, алармы,
логгер и веб-телеметрия.

Виджет не знает, откуда пришло значение — он привязан к строковому ID сигнала
(`engine.rpm`, `sensor.oil_p`, `calc.boost`), который при загрузке конфига хешируется
в `uint16` индекс. Это даёт три вещи бесплатно: режим симуляции в редакторе, замену
источника (CAN → внешний датчик) без правки лейаута и единый механизм алармов.

Синхронизация между ядрами: запись слота в коротком критическом участке, UI на каждом
кадре снимает снапшот нужных ему слотов. Без блокировок на стороне рендера.

### 3. Конфигурация
Всё в LittleFS, разбито по назначению:

```
/cars/<id>.json      профиль машины: шина, CAN ID, разбор битов, OBD-запросы
/layouts/<id>.json   лейаут: экраны, виджеты, привязки, тема, алармы
/device.json         wifi, яркость, единицы, активный лейаут и профиль
/www/                собранный веб-редактор (gzip)
/logs/               логи и сырые CAN-дампы
```

Парсинг — ArduinoJson 7 с аллокатором в PSRAM. Схемы версионируются полем `schema`,
при повышении версии применяются миграции при загрузке.

### 4. CAN
Профиль машины задаёт, какие ID вообще пропускать аппаратным фильтром приёма — иначе
поток 500 кбит/с забьёт CPU бесполезной работой. Дальше по ID ищем правило разбора в
хеш-таблице и извлекаем сигналы (start bit, длина, endianness, scale/offset,
мультиплексор).

Два режима работы, оба описываются в профиле:
- **пассивный** — слушаем широковещательные кадры (по умолчанию, ничего не передаём);
- **запросы** — OBD-II mode 01 и при необходимости mode 22 / UDS ReadDataByIdentifier
  поверх ISO-TP, с ограничением частоты и явным включением пользователем.

Обязательны: восстановление после bus-off, счётчики ошибок, и полная независимость
рендера от состояния шины (пропала шина → виджеты показывают «нет данных», UI живёт).

**Режим обнаружения (discovery).** Для новой машины: запись сырых кадров в лог плюс
веб-вид «сниффер» с подсветкой ID, чьи байты меняются, пока крутишь двигатель или
жмёшь педаль. Так профили добавляются без реверса вручную.

### 5. Рендер

**Выбран свой рендерер поверх `Arduino_GFX`** (вариант B). Обоснование и отвергнутая
альтернатива с LVGL — в `docs/RENDER_AB.md`.

Устройство: полный фреймбуфер 466×466 RGB565 в PSRAM, рисуем все виджеты, затем один
блит на панель. Слои — `display_hw` (панель и канва), `signal_bus` (данные),
`layout_store` (JSON из LittleFS), `widget_render` (отрисовка).

Открытые вопросы: текст пока встроенным шрифтом 6×8 с целым масштабом, антиалиасинга
нет, «грязные» прямоугольники и синхронизация по TE-пину не реализованы —
всё это оптимизации поверх работающего пайплайна.

**Выгорание AMOLED** — отдельная забота: сдвиг пикселей на несколько px по таймеру,
ограничение площади ярко-белых зон в темах, автояркость, гашение по пропаже зажигания.

### 6. Задачи и ядра

| Ядро | Задача | Приоритет | Что делает |
|---|---|---|---|
| 0 | `can_rx` | высокий | чтение очереди TWAI, разбор сигналов |
| 0 | `sensors` | средний | опрос I2C-датчиков и PCNT, фильтрация |
| 0 | `net` | низкий | HTTP API, WebSocket телеметрии, OTA |
| 0 | `logger` | низкий | запись логов пачками |
| 1 | `ui` | средний | рендер, тач, алармы |

### 7. Веб-слой
REST для конфигов (`GET/PUT /api/layout`, `/api/car`, `/api/device`), WebSocket `/ws`
для телеметрии на 10–20 Гц и живого предпросмотра правок. Телеметрия — компактный
бинарный кадр (id + значение), конфиги — JSON. Устройство поднимает точку доступа
`Tracraft-Dash` и отвечает на `http://192.168.4.1`, в домашней сети доступно по mDNS.

### 8. OTA
Два независимых обновления через веб: прошивка (`app0`/`app1`, откат при неудачном
старте) и образ файловой системы. Плюс импорт/экспорт лейаутов и профилей отдельными
файлами, чтобы пресетами можно было делиться.

## План памяти (ориентировочно)

| Что | Где | Размер |
|---|---|---|
| Буферы отрисовки LVGL, 2×40 строк | внутренняя RAM | ~75 КБ |
| Полный фреймбуфер (если свой рендерер) | PSRAM | 434 КБ |
| Шина сигналов, 256 слотов | внутренняя RAM | ~6 КБ |
| История для графиков | PSRAM | по потребности |
| Разбор JSON | PSRAM | ~64–256 КБ на время загрузки |
| Очередь CAN | внутренняя RAM | 64 кадра |

## Разделы флеша (16 МБ)

`nvs` 20 КБ · `otadata` 8 КБ · `app0` 4 МБ · `app1` 4 МБ · `littlefs` ~7.9 МБ ·
`coredump` 64 КБ. Подробности — в `partitions.csv`.

## Что осознанно откладываем

Логирование заездов, лап-таймер с GPS, темы и брендинг, поддержка CAN-FD (внешний
MCP2518FD), нативное приложение. Архитектура не должна этому мешать: логгер — ещё один
подписчик шины сигналов, CAN-FD — ещё одна реализация интерфейса шины, приложение —
ещё один клиент того же API.
